# Premium direction — research proposal, not an offer

Keep the community reader useful: offline opening/reading, Markdown editing, basic OCR, voice import, keyboard access and data export. Do not remove accessibility essentials, force document upload or add artificial reading limits to create a paid tier.

## Candidate paid value

| Candidate | User benefit | Validation before committing |
|---|---|---|
| Batch audiobook projects | Queue documents, resume jobs, organise chapters and export consistent audio | Ask prospective users to test a real long project; measure failure recovery and output quality |
| Advanced study workspace | Linked notes, collections, saved reading queues and reusable study layouts | Test whether it reduces repeated setup without confusing the simple reader |
| Pronunciation workbench | Preview, compare and share document-specific dictionaries | Verify language/number handling and safe import/export |
| Advanced OCR workflows | Review uncertain text, correct reading order and process page ranges in batches | Validate on varied scanned layouts; never promise perfect figures/tables |
| Optional expressive engine | Higher-quality voices where hardware supports them | Benchmark Qwen/Piper options and clear exact model/speaker rights first |
| Curated original voice packs | Consented voices with clear credits, model cards and predictable offline behavior | Complete the recording/training pilot and licence review before selling |

Prefer durable convenience features over recurring cloud costs for the first paid offer. Cloud services would need separate consent, privacy information and a sustainable usage policy. Do not bundle ongoing cloud costs into an unlimited lifetime promise.

## Proposed purchase policy to validate

A one-time purchase grants perpetual use of the purchased major version and updates released for that major version. A later major version may be a separate optional purchase; the older version should continue working on supported systems. Avoid the ambiguous phrase “lifetime updates” without naming the major-version boundary. Define supported operating systems, security-maintenance policy, offline activation or absence of activation, device limits if any, refund rules and discontinuation handling before sale. No final price is proposed.

## Open-source architecture constraint

Charging for open-source builds, support or permitted assets is compatible with the project's direction. The current AGPL/GPL components do not become proprietary because the product is paid. Do not promise closed-source premium code or use a process/plugin boundary as assumed licence avoidance. Reassess the exact implementation and all contributor rights before choosing a separate closed-source edition. Original voice assets require their own rights and terms; the software licence alone does not settle them.

## Small validation programme

Interview five to ten potential readers using original sample content. Ask which task they repeat, what currently wastes time and which proposed workflow would solve it. Show one batch-project prototype before discussing payment. Record objections, willingness to use the feature and support burden. A small interview sample is directional feedback, not market-size evidence.

Propose a feature only when it has a concrete workflow, acceptance checks, maintenance estimate, dependency/rights review and a budget. Keep basic usability fixes in the community roadmap. No subscriptions, prices, accounts, checkout pages, paid development commitments or voice purchases have been launched by this proposal.
